# Taz: Wanted HD

HD remaster mod for the 2002 PC release of Taz: Wanted (Blitz Games, Babel engine, Direct3D 8, MSVC 6).
Shape: a loader DLL and asset packs applied to the user's own copy; later an optional modern render mode by hooking Babel's PC render layer (`C:\Babel\PC\Src\bDisplay`, `bActor`).

## Local setup
- Local paths live in `dev.env` (git-ignored; see README.md), which `tools/run-dev.sh` and `tools/mount-cd.sh` read. Never put machine paths in tracked files.
- Pristine install: a retail install kept outside the repo (never modify). `taz.exe` linked 2002-07-22.
- Dev install: `TAZ_GAME` (btrfs reflink copy of the pristine one). `d3d8.dll` there is a symlink to `build/d3d8.dll`; it writes `taz-hd.log` in the game folder.
- Wine prefix: `WINEPREFIX`, Proton-format (system `wine` can't open it; edit `*.reg` directly with nothing running). The game reads its folder from `Software\Infogrames\TazWanted\Release` `Location` (80-byte buffer); the proxy now answers that itself (`startup.c`: makes the game folder current and returns "."), so no registry entry is needed.
- The game checks for its CD (volume label). Disc image: `ISO` (label TAZWANTED; its exes are byte-identical to the install). `tools/mount-cd.sh` mounts it and points the prefix's `D:` at it.
- Lutris entry: dev install, that prefix, override `d3d8=n,b`, pre-launch `tools/mount-cd.sh`, arg `Launched`.
- Unpatched, `taz.exe` alone starts `TazLauncher.exe`, whose Play runs `taz.exe Launched`. The proxy patches the check (0x4aa0dc) so it always starts as if `Launched` was given; the argument is now optional. A taz.exe with a different link timestamp gets a one-time warning box (`version_warning` in the ini).
- The CD check (volume label TAZWANTED, FUN_004a1de0 at each scene load) is still in place on purpose: removing it would turn the public mod into a no-CD crack.
- `tools/run-dev.sh [--headless]` launches like Lutris; `--headless` runs in an invisible gamescope (usually X display `:2`; `qa/key.sh` finds it), with sound sent to a silent `taz-hd-silent` sink (the user wants tests muted; unload it with `pactl unload-module module-null-sink` when done). Hold keys ~120 ms (`xdotool keydown/keyup`) or the game misses them. Screenshots: F12, or `echo N > <game>/taz-hd/shot` (N>1: N frames at 1/8 size, timestamps in the log).
- Settings: `<game>/taz-hd.ini` `[taz-hd]` resolution (auto = desktop, written into taz.dat), hd_textures, hd_models (ini only; 0 draws the original models), vsync, smooth_characters, fps_limit, menu_text_speed (default 3), passthrough (1 = no patches, for comparing with the original). They are rows in the game's own menus (`menu.c`, all apply live; HD textures stay loaded while off). Keep `=` out of comment lines: Wine's profile writer rewrites them.
- Diagnostics in `taz-hd.log`: crashes (module + offset, registers, last SetTexture calls), game asserts, scene loads, CD check failures. The DLL often loads away from its preferred base 0x70180000, so map crash addresses by the logged offset.
- The frontend starts an attract demo after ~23 s idle (scenes 5, 0, 1); keep that in mind when testing idle behaviour.
- Texture pipeline (in the proxy): fingerprint = FNV-1a 64 over (w, h, D3DFORMAT as 3 u32) + level-0 rows, `|1`. Pak textures are uploaded unchanged: format 25 (A1R5G5B5), or 21 (A8R8G8B8) for the ~70 with byte 8 of the header = 1 (soft sprites, mostly `.tga` in resTex; 3 = 16-bit), so `tools/pak.py textures` writes the same fingerprints to `fingerprints.tsv`; copy it to `<game>/taz-hd/fingerprints.tsv`. Replacement lookup: `<game>/taz-hd/textures/<pak>/<path>.png` by name, then `<fingerprint>.png`. Any size; mipmaps generated. If `<game>/taz-hd/dump/` exists, every uploaded texture is saved as `<fingerprint>.png` (about 85% of a level's textures come from paks).
- Live resolution/vsync (`display.c`): when a change is pending, TestCooperativeLevel reports lost, then needs-reset, so the game runs its own alt-tab recovery (FUN_0056e4f0: releases textures, render targets, vertex buffers, calls Reset with its params at 0x7420a4, rebuilds). In Reset we put in the new size/interval, unbind everything, delete the overlay's state block (it held the game's released vertex buffer, which blocked Reset under Wine), call the game's index buffer suspend/resume (0x573400/0x573510), and restore render-target depth buffers (the game's path frees them, zeroes +0x84 and never recreates them; we put a non-zero mark back). After a size change: 0x741f74.. screen globals, FUN_0056afb0, 0x6c6b78/7c, FUN_0048fac0, aspect, FUN_00435530 per player. "auto" is the desktop size read at startup. Tested: 11 size changes and vsync on/off in a level, no crash; textures recreated, so an older quicksave is refused.
- Settings in the game's menus (`menu.c`): the call that adds the Widescreen row on Game Options (0x525156, ADD_TEXT 0x544640 thiscall(page, string, new_row)) instead adds our rows and returns a throwaway item; on the pause options page our rows go in before Exit Game (0x4c5bb7, ADD_ITEM 0x5445d0). Row text: SET_TEXT (0x540350, cdecl, printf-style from string table 0x6c8c08+0x20, 16-byte entries) with entry 0x58e pointed at our wide text for the call. Events arrive at the nearest page up the +0x34 chain with a callback at +0x110 (cdecl, {item, event}: 0 highlight, 2 Select); we wrap it and pass others on. The line under the rows is a book of named pages (FUN_00549370 thiscall(book, name, 0); an unknown name changes nothing): Game Options' blank "NULL" page and the pause menu's unused "VIBRATION" page carry our descriptions (their text items captured at 0x5254f2 and 0x4c5cdc). Popups open: 0x739b74 / 0x702310.
- Aspect (`widescreen.c`): always the screen's shape. The 4:3 branch of FUN_0048fd20 writes the screen aspect; its entry is patched so the game's own Widescreen option (forced 16:9, plus a different FOV constant) is always off. `widescreen_apply()` re-runs it after a size change.
- Engine facts: current scene byte 0x704cf0 (table of names at 0x646d9c; 0 language, 1 frontend). Main loop timing at 0x4dc13c..0x4dc1ae: fps 0x642cdc, seconds per frame 0x6f4c48, 60/fps 0x6c6c14, unpaused frame time 0x6c7ee0 (menu page effects). Timer calibrates RDTSC at startup (0x578450), accurate here. Aspect bytes 0x6c6b88/89, screen size 0x6c6b78/7c.
- Texture memory: replacements are counted per live game texture (hooked texture Release, vtable slot 2) and freed when the last one goes; they reload from disk if it comes back. Kept forever (before 2026-11-03) each new level added ~240 MB and the game crashed by the fifth different level in one session (32-bit, ~4 GB). Measured after the fix: 2.47-2.51 GB through ten level loads, no crash; 60-round quicksave stress passed.
- Scrolling textures (waterfalls, escalators): never read the table directly, it can hold freed handles (that crashed during the attract demo); the proxy hooks the copy call at 0x4db7d1 and records the live textures. Table at 0x705f30, 6 x {big handle, small handle, speed u, speed v, offset u, offset v}; each frame FUN_00574960 copies a window (offset * small size) of the big texture into the small one. The proxy binds the HD big texture with a texture transform instead. Babel texture handle: Direct3D texture at **(handle+0x24).
- Menu item effects (PageItemFX.cpp: slide-in FUN_00537840, letters flying off, fades) are time-based, ~2.25 s from key press to the new items settling when opening Game Options. menu_text_speed scales their clock and runs the slide-in update that many times per frame (it caps each step at 0.05 s and damps its landing wobble per call, so clock scaling alone stalls near 1.5x). Measured settle time at 40 fps: 1x ~90 frames, 2x ~45, 3x ~24. Don't speed up the frontend frame rate: that also speeds the camera flight and characters.
- Only the three logo idents are Bink videos (640x480, 25 fps); the story intro is in-engine. The game copies frames into the back buffer at 2x, centred (FUN_00478290); `video.c` takes the copy and draws it scaled to the screen height, using `taz-hd/videos/<name>/NNNN.jpg` from `tools/videos.py` when present (Bink frame numbers count from 1, matching ffmpeg's order; checked on frame 100 of each video).
- Quicksave (`quicksave.c`): F5/F9 copy the whole bInitHeap block (base 0x73f704, size 0x73f79c, 60 MB, allocated once) plus .data/.data1 (0x630000..0x75e000) between frames, in place of the call at 0x4dc12a; other threads are suspended during the copy. On load the frame clock and every critical section taz.exe initialised keep their current contents. Direct3D textures and sound buffers are outside that memory, so a load is refused when the scene changed or taz.exe created a texture since the save. Measured: ~11 ms per copy; 41 loads during random play with no crash; music continues across loads.
- Characters (`smooth.c`): drawn with DrawPrimitive (strips and lists of a few triangles, one bone palette each) from managed vertex buffers of 52-byte vertices (FVF 0x115c: position, 3 weights, UBYTE4 palette offsets, normal, colour, uv) through vertex shaders sharing one declaration. Shader 0xf0000006-style: skins with 3 bones (palette at c0.., 3 registers per bone), ramp u = max(0, N.L with light c48), ramp row c48.w; the outline pass (cull CW) pushes the vertex out along the normal by c49.w. Taz is ~2,000 triangles in ~460 batches. Smoothing swaps each batch for a cached PN-triangle copy, 3x3 per triangle; shared edges are computed from a fixed end so neighbouring batches match bit for bit. Before tessellating, each buffer's normals are evened out like `tools/normals.py` (6 nearest positions, 3 rounds, neighbours facing more than 60 degrees away ignored, hard-edge corners kept), at most 6.5 ms once per model; replacement models skip it (`smooth_keep_normals`). Checked on Taz's original model: same clean shadows as the Blender-evened one. Cache is keyed by (buffer, start, count, type) and dropped when a buffer is created at a cached address. Quickload stress: one heap crash in ntdll in ~150 loads with smoothing on (none in 2 runs since), cause unknown.
- Models (`mesh.c`): `taz-hd\meshes\<FNV-1a of the vertex buffer>.bin` replaces a whole character. Every pass (textured, then outline) draws the same batches in the same order, so the file lists them; each skipped batch hands over its bone matrices (bone i = register r of batch b) and texture, and the last one draws the replacement in groups of up to 16 bones through `smooth_draw`. Taz's buffer is b53721ca228ead11 (same every run). His hands: palm bone, three fingers of two bones each and a two-bone thumb, all rigidly skinned; `tools/hands.py` swaps the six-sided fingers for 10-sided tapered ones with knuckles and blended joint weights (thickness from the old knuckle ring, x1.08, since smoothing puffs the old ones out in game). Checked in game across idle poses (claws, fists) with smoothing on. Cel-shading band edges follow the vertex normals (u = N.L per vertex), so finer tessellation (LEVEL 5) and quadratic PN normals changed nothing visible; `tools/normals.py` averages the model's normals with neighbours (3 rounds, hard edges over ~30 degrees kept except at the ears' inner material, so smoothing rolls their rims round), which made Taz's face, hair and belly shadows clean shapes instead of ragged patches.
- Springs (`mesh.c`, file format TZM2): extra bones after the game's, each hanging off a game bone with a pivot and tip in bind space. Once per frame the tip is pulled toward where the parent puts it (stiffness, damping against the parent's own velocity, so steady runs don't drag it), and the spring bone is the parent turned about the pivot by amount x the lag angle, eased toward limit with tanh. `tools/springs.py` gives Taz four (ears, top fur, tail); swings measured in a run: ears ~2 degrees idle, up to ~20 while running and stopping. Damping against world velocity left them pinned at their limits, and Taz's run animation bobs his head hard, hence amount < 1.
- Input (Babel bInput, DirectInput8): logical channels with up to 6 bindings each; FUN_00568630 creates one (value int at +0x14, ±0x7ff8), FUN_00568860 biBindInput(channel, code, code2) binds. Physical codes (FUN_0057be60): 2-4 mouse buttons, 5/6/7 mouse X/Y/wheel (DIMOUSESTATE at 0x751548, mouse device 0x7513a4), 10-41 joystick buttons, 0x2a-0x2f joystick axes, 0x36-0xa0 keys (code -> DIK via the dword table at 0x658770 + code*4). Player pads: 0x6c8090 (P1), 0x6c83b0 (P2), set up by FUN_00489ed0; channel pointers at pad+0x38 x1, +0x3c y1, +0x40 x2, +0x44 y2, +0x60 cross (Jump, C), +0x64 triangle (Bite, R), +0x68 circle (Spin, F), +0x6c square (Rant, D), +0x70 L1 (camera left, E), +0x74 L2 (Tiptoe, X), +0x7c R1 (camera right, T), +0x80 R2 (look around, V), +0x88 start (P), +0x8c select (map, Space); +0xa0.. are the debounced copies. Keyboard defaults: FUN_0048c100 (arrows move; the camera stick has no keys). FUN_00489b90 turns channels into pad floats each frame: [2]/[3] left/right magnitude, [4]/[5] left x/y, [6]/[7] right x/y (-1..1).
- Camera control: FUN_004e0f00 (camera at param+4, pad at param+8). L1/R1 swing the camera around Taz at 0x5f7364/fps rad per frame; the right stick swings at that rate times x and tilts via camera+0x64 = camera+0x2e0 + -y * 0x5f73ec (springs back at 0). Camera flags at +0x74 (0x800 look-around mode, 0x8000 stick-only). Look-around (first person) is FUN_004e19a0 / FUN_004e1c00.
- Controls (`controls.c`, setting `controls` wasd|classic, keys per action `key_*` in the ini): wraps the keyboard defaults call (0x48ad3c, 0x48ad74); for player 0 it takes each layout key off every channel FUN_0048c100 binds, then binds it to its action. Live changes (`controls_apply`) clear those channels, rerun FUN_0048c100 and bind the layout again. Channel bindings: slot k at +0x24 + k*0x1c (codes), slot count at +0xcc; wraps the camera control call (0x480e5d) to add mouse X/Y to the pad's stick floats for that call only (right stick normally, left stick in look-around, flag 0x800, whose turn sign is opposite) and turns the camera position (+0x00) by the same angle the game gave its destination (+0x20), since the game eases toward it. Single player uses pad 0x6c83b0; check pad+0x180 (player index), not the address. The DirectInput mouse goes exclusive (hidden, unlimited deltas) only while the camera control ran in the last 2 frames. Tested headless with xdotool mousemove_relative. Map: 0x4a77f1 opens it (FUN_004c7df0) when the debounced select channel (pad+0xcc, 0x6c847c) is set, FUN_004cbcb0 allows it, and scene 0x704cf0 is not 0, 1, 3, 7, 8, 0xc, 0xd, 0x11, 0x13-0x1d; the zoo hub is scene 3, so no map there. Tab sets that channel (logged 0x7ff8).
- Controls page (`menu.c`): the Game Options builder (FUN_00524db0, called at 0x521249 with the frontend block 0x739b08) is wrapped to add a page "TAZHD_KEYS" to the frontend book (frontend+0x68 = *0x739b70) with ADD_PAGE (0x548ed0, thiscall(book, name, 0, 0, 0)). Shown with SHOW_PAGE (0x549370, thiscall(book, name, 0)) after selecting a row (0x5449c0, thiscall(page, item); page+0x130 is the highlighted item). Page events: 0 highlight, 1 unhighlight, 2 Select, 3 Back (item NULL). While it is open the Game Options state (*(*0x739b50)) is held at 7 so its update ignores Back; close at Present, after that update, or it also backs out to the main menu. Key capture wraps the device read at 0x568b25: reads DIK states (0x751438) and mouse buttons (0x751554), then clears them (and 0x751544) so menus see nothing.
- Ghidra project lives in `re/` (ignored). `make` builds the proxy with mingw-w64.
- Scene jumps for tests (`capture.c`): a `taz-hd\scene` file holding a scene number calls FUN_004a9730(0x6c8c18, scene), the game's scene change (the attract demo uses it), between game frames from the quicksave hook; it is ignored outside play (scene < 2). Delete the file before calling: loading runs game frames that come back to the hook. FUN_004b8de0 (logged as "saving on the way to scene") is the save writer that runs on scene changes, not the change itself. Scene changes save the game, so back up TazWanted.sav.
- Mesh capture (`capture.c`): a `taz-hd\capture` file (optionally holding a frame count) records character draws: each vertex buffer once, then per draw its range, stage-0 texture fingerprint and vertex shader constants c0-c95. Constants: c0-c47 bone matrices (3 rows each, bind pose to world; vertex palette offsets are register numbers), c48 light, c49 outline, c92-c95 view-projection. Buffers hold the bind pose (a T-pose for Taz, Y up, ~315 units tall). Taz's buffer has 3,164 vertices (1,039 positions, 2,006 triangles, ~46 bones) and 7 textures; textureless draws are the outline pass. `blender -b -P tools/meshview.py -- <capture> 0 <out.blend>` rebuilds the biggest buffer as a mesh with a vertex group per bone (bones found by matching matrices across batches); `tools/meshshot.py` renders a .blend from four sides, textured and wireframe. Bone poses change every frame at 60 fps (no stepped animation).
- `tools/pak.py list|unpack|textures` reads `.pc` paks; `textures` writes each unique texture once as PNG plus `index.tsv` (all occurrences). Output goes in `extracted/` (ignored). Mostly 64-128 px, max 512; 7,239 unique. `tools/upscale.py` leaves `ramps.png` alone (a cel-shading lookup strip for Taz and She-Devil; upscaling it made their shading blotchy) and only enlarges mostly see-through sprites smoothly (the upscaler hardens glows).

## Testing and release
- Test rig scripts live in `qa/` (untracked): `stop.sh`, `key.sh` (finds gamescope's X display), `launch.sh` (to the main menu), `tolevel.sh` (into slot One's level), `qsfuzz.sh <rounds>` (random play with F5/F9), `step.sh <out.jpg> [wait] [keys]` (screenshot), `tomenu.sh` (to main menu via `similar.py` + `ref-mainmenu.jpg`), `idletest.sh`, `measure.sh`/`analyze.py` (menu timing), `fresh.sh <prefix>` and `player.sh <prefix> <game dir>` (no-argument start, like a player). Back up `TazWanted.sav` before runs that might reach a save.
- Release: `tools/package.sh <version>` builds `dist/taz-wanted-hd-<version>.zip` (DLL, `extracted/upscaled` as `taz-hd/textures`, `fingerprints.tsv`, `extracted/videos`, `package/README.txt`, LICENSE). Player test: reflink-copy the pristine install somewhere with a long path, unzip into it, run `qa/player.sh` with a fresh prefix (mount the ISO into it with `WINEPREFIX=<prefix> tools/mount-cd.sh`). 0.1 passed this on 2026-10-30 up to the in-engine intro. Release plan: mod zip only (player brings the game); never ship game files.

## Rules
- The game files are verified retail (2026-10-29): `taz.exe` and `TazLauncher.exe` are byte-identical to the disc and known to VirusTotal since 2009 with 0 detections; `binkw32.dll` has 1/71 (Cynet heuristic, first seen 2009). Agents may launch the dev install for testing; recheck hashes if the install is replaced.
- Never commit game binaries, pak files, or anything extracted from them. Public releases ship only our code and our assets.
