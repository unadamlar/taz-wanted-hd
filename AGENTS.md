# Taz: Wanted HD

HD remaster mod for the 2002 PC release of Taz: Wanted (Blitz Games, Babel engine, Direct3D 8, MSVC 6).
Shape: a loader DLL and asset packs applied to the user's own copy; later an optional modern render mode by hooking Babel's PC render layer (`C:\Babel\PC\Src\bDisplay`, `bActor`).
The modern-look remaster work lives on the `look-test` branch; its plan and state are in `REMASTER.md`.

## Local setup
- Local paths live in `dev.env` (git-ignored; see README.md), which `tools/run-dev.sh` reads. Never put machine paths in tracked files.
- Pristine install: a retail install kept outside the repo (never modify). `taz.exe` linked 2002-07-22.
- Dev install: `TAZ_GAME` (btrfs reflink copy of the pristine one). `d3d8.dll` there is a symlink to `build/d3d8.dll`; it writes `taz-hd.log` in the game folder.
- Wine prefix: `WINEPREFIX`, Proton-format (system `wine` can't open it; edit `*.reg` directly with nothing running). The game reads its folder from `Software\Infogrames\TazWanted\Release` `Location` (80-byte buffer); the proxy now answers that itself (`startup.c`: makes the game folder current and returns "."), so no registry entry is needed.
- Lutris entry: dev install, that prefix, override `d3d8=n,b`, arg `Launched`.
- Unpatched, `taz.exe` alone starts `TazLauncher.exe`, whose Play runs `taz.exe Launched`. The proxy patches the check (0x4aa0dc) so it always starts as if `Launched` was given; the argument is now optional. A taz.exe with a different link timestamp gets a one-time warning box (`version_warning` in the ini).
- `tools/run-dev.sh [--headless]` launches like Lutris; `--headless` runs in an invisible gamescope (each game gets its own X display, `:2` upward; `qa/game.sh display` finds it), with sound sent to a silent `taz-hd-silent` sink (the user wants tests muted; unload it with `pactl unload-module module-null-sink` when done). Hold keys ~120 ms (`xdotool keydown/keyup`) or the game misses them. Screenshots: F12, or `echo N > <game>/taz-hd/shot` (N>1: N frames at 1/8 size, timestamps in the log). Trigger files (`shot`, `capture`, `scene`, `costume`, `complete`) are only read with `tests=1` in `taz-hd.ini`; the dev install and the `taz-agents` copies have it, a new copy needs it, players' games never look.
- Settings: `<game>/taz-hd.ini` `[taz-hd]` resolution (auto = desktop, written into taz.dat), hd_textures, hd_models (ini only; 0 draws the original models), vsync, antialiasing (0/2/4/8, default 4), smooth_characters, taz_style, fps_limit, menu_text_speed (default 3), passthrough (1 = no patches, for comparing with the original). They are rows in the game's own menus (`menu.c`, all apply live; HD textures stay loaded while off). Keep `=` out of comment lines: Wine's profile writer rewrites them.
- Diagnostics in `taz-hd.log` (lines end in CRLF: anchor greps with `.\?$`): crashes (module + offset, registers, last SetTexture calls), game asserts, scene loads. The DLL often loads away from its preferred base 0x70180000, so map crash addresses by the logged offset.
- Renderer (`third_party/d3d8to9`, changes in its CHANGES.md; `src/d3d8/d3d9.cpp`): `Direct3DCreate8` wraps a real IDirect3D9 in d3d8to9, so hooks still patch IDirect3DDevice8 slots, and `passthrough=1` also runs on D3D9. Vertex shader handles are `pointer>>1 | 0x80000000` (`IS_VERTEX_SHADER`); the `f0000006`-style names below are the old DXVK handles. On Reset the game deletes and remakes its vertex shaders, so never keep their handles. Fullscreen sizes the display doesn't offer fail Reset with 0x8876086a and the old size stays (headless gamescope: 1600x1000 refused; 1920x1200, 2560x1600, 2880x1620 work). Test trigger: `taz-hd\display` holding `W H V`.
- Remaster look (`look.c`, `hd.c`, HLSL in `src/d3d8/shaders/`, compiled into the checked-in `look_shaders.h`): HUD and menus are FVF `0x152` draws with `ZFUNC ALWAYS`. Paused frames draw their sky that way first, so the HUD only starts at an `ALWAYS` draw after 3D has begun. CPU-projected sparkles (`XYZRHW`) are depth-tested inside the 3D pass. A third character shader kind has no normal (`c48` camera, `c49` fog, `c50` colour); the elephant uses it and has no texture. A scene change can free character vertex buffers after their draws were recorded, so never redraw a buffer only we still hold (it crashed DXVK's allocator on most reloads). The device uses mixed vertex processing (flags `0x80`). Tutorial books draw an additive glow and ribbon (`resTex/powerupglow`, FVF `0x1c4`, SRCALPHA/ONE) that tints much of the view up close in every look. Paper book screens draw a 2D backdrop before their 3D page, so such a frame must stay out of the HDR pass. Red marks on the hub's paths are painted into the path textures (up to 59% of `zoohubpath8`).
- Merged world (`merge.c`, Remaster look): the hub's static world is one unbroken run of ~7,250 draws from one vertex buffer, already in texture order (172 textures). Each becomes a lookup, and the pieces issued that frame are drawn at the first draw that isn't a piece, so order against other draws holds. The game picks wrap or clamp per draw (44 textures use more than one), so that is part of a merged run's key.
- The frontend starts an attract demo after ~23 s idle (scenes 5, 0, 1); keep that in mind when testing idle behaviour.
- Texture pipeline (in the proxy): fingerprint = FNV-1a 64 over (w, h, D3DFORMAT as 3 u32) + level-0 rows, `|1`. Pak textures are uploaded unchanged: format 25 (A1R5G5B5), or 21 (A8R8G8B8) for the ~70 with byte 8 of the header = 1 (soft sprites, mostly `.tga` in resTex; 3 = 16-bit), so `tools/pak.py textures` writes the same fingerprints to `fingerprints.tsv`; copy it to `<game>/taz-hd/fingerprints.tsv`. Replacement lookup: `<game>/taz-hd/textures/<pak>/<path>.png` by name, then `<fingerprint>.png`. Any size; mipmaps generated. If `<game>/taz-hd/dump/` exists, every uploaded texture is saved as `<fingerprint>.png` (about 85% of a level's textures come from paks).
- Live resolution/vsync (`display.c`): when a change is pending, TestCooperativeLevel reports lost, then needs-reset, so the game runs its own alt-tab recovery (FUN_0056e4f0: releases textures, render targets, vertex buffers, calls Reset with its params at 0x7420a4, rebuilds). In Reset we put in the new size/interval, unbind everything, delete the overlay's state block (it held the game's released vertex buffer, which blocked Reset under Wine), call the game's index buffer suspend/resume (0x573400/0x573510), and restore render-target depth buffers (the game's path frees them, zeroes +0x84 and never recreates them; we put a non-zero mark back). After a size change: 0x741f74.. screen globals, FUN_0056afb0, 0x6c6b78/7c, FUN_0048fac0, aspect, FUN_00435530 per player. "auto" is the desktop size read at startup. Tested: 11 size changes and vsync on/off in a level, no crash; textures recreated, so an older quicksave is refused.
- Anti-aliasing (`display.c`): MSAA through the present parameters at CreateDevice and in the Reset above (highest count up to the setting that CheckDeviceMultiSampleType allows for back and depth buffer; DISCARD swap, no lockable back buffer). The engine has its own dormant 4x mode (bStartDisplay 0x56da17: display flag 0x40 in 0x741f70 sets MultiSampleType 4, DISCARD, Flags 0), not reachable from taz.dat or config.exe. The game locks the back buffer (0x741fc8) for each Bink frame and retries forever on failure (0x4782bd); `video.c` skips that lock, since its BinkCopyToBuffer hook always copies into its own 32-bit buffer. Screenshots resolve via CopyRects into a plain render target (DXVK's GetRenderTargetData rejects multisampled sources). Measured at 2880x1800 in the zoo hub: ~113 fps at off, 4x and 8x alike (the limit is elsewhere).
- Settings in the game's menus (`menu.c`): the call that adds the Widescreen row on Game Options (0x525156, ADD_TEXT 0x544640 thiscall(page, string, new_row)) instead adds our rows and returns a throwaway item; on the pause options page our rows go in before Exit Game (0x4c5bb7, ADD_ITEM 0x5445d0). Row text: SET_TEXT (0x540350, cdecl, printf-style from string table 0x6c8c08+0x20, 16-byte entries) with entry 0x58e pointed at our wide text for the call. Events arrive at the nearest page up the +0x34 chain with a callback at +0x110 (cdecl, {item, event}: 0 highlight, 2 Select); we wrap it and pass others on. The line under the rows is a book of named pages (FUN_00549370 thiscall(book, name, 0); an unknown name changes nothing): Game Options' blank "NULL" page and the pause menu's unused "VIBRATION" page carry our descriptions (their text items captured at 0x5254f2 and 0x4c5cdc). Popups open: 0x739b74 / 0x702310.
- Aspect (`widescreen.c`): always the screen's shape. The 4:3 branch of FUN_0048fd20 writes the screen aspect; its entry is patched so the game's own Widescreen option (forced 16:9, plus a different FOV constant) is always off. `widescreen_apply()` re-runs it after a size change.
- Engine facts: current scene byte 0x704cf0 (table of names at 0x646d9c; 0 language, 1 frontend). Main loop timing at 0x4dc13c..0x4dc1ae: fps 0x642cdc, seconds per frame 0x6f4c48, 60/fps 0x6c6c14, unpaused frame time 0x6c7ee0 (menu page effects). Timer calibrates RDTSC at startup (0x578450), accurate here. Aspect bytes 0x6c6b88/89, screen size 0x6c6b78/7c.
- Texture memory: replacements are counted per live game texture (hooked texture Release, vtable slot 2) and freed when the last one goes; they reload from disk if it comes back. Kept forever (before 2026-11-03) each new level added ~240 MB and the game crashed by the fifth different level in one session (32-bit, ~4 GB). Measured after the fix: 2.47-2.51 GB through ten level loads, no crash; 60-round quicksave stress passed.
- Scrolling textures (waterfalls, escalators): never read the table directly, it can hold freed handles (that crashed during the attract demo); the proxy hooks the copy call at 0x4db7d1 and records the live textures. Table at 0x705f30, 6 x {big handle, small handle, speed u, speed v, offset u, offset v}; each frame FUN_00574960 copies a window (offset * small size) of the big texture into the small one. The proxy binds the HD big texture with a texture transform instead. Babel texture handle: Direct3D texture at **(handle+0x24).
- Menu item effects (PageItemFX.cpp: slide-in FUN_00537840, letters flying off, fades) are time-based, ~2.25 s from key press to the new items settling when opening Game Options. menu_text_speed scales their clock and runs the slide-in update that many times per frame (it caps each step at 0.05 s and damps its landing wobble per call, so clock scaling alone stalls near 1.5x). Measured settle time at 40 fps: 1x ~90 frames, 2x ~45, 3x ~24. Don't speed up the frontend frame rate: that also speeds the camera flight and characters.
- Only the three logo idents are Bink videos (640x480, 25 fps); the story intro is in-engine. The game copies frames into the back buffer at 2x, centred (FUN_00478290); `video.c` takes the copy and draws it scaled to the screen height, using `taz-hd/videos/<name>/NNNN.jpg` from `tools/videos.py` when present (Bink frame numbers count from 1, matching ffmpeg's order; checked on frame 100 of each video).
- Quicksave (`quicksave.c`): F5/F9 copy the whole bInitHeap block (base 0x73f704, size 0x73f79c, 60 MB, allocated once) plus .data/.data1 (0x630000..0x75e000) between frames, in place of the call at 0x4dc12a; other threads are suspended during the copy. On load the frame clock and every critical section taz.exe initialised keep their current contents. Direct3D textures and sound buffers are outside that memory, so a load is refused when the scene changed or taz.exe created a texture since the save. Measured: ~11 ms per copy; 41 loads during random play with no crash; music continues across loads. The 40 sound channels at 0x750040 (0x54 each, DirectSound buffer at +0x30) are not restored: a saved pointer can be a buffer the game has released, and FUN_0057ae00 then loops on Release forever or crashes in DirectSound (F5, walk, F9 froze 15 of 17 runs before this, on `master` too). Sounds started after the save are stopped at load.
- Characters (`smooth.c`): drawn with DrawPrimitive (strips and lists of a few triangles, one bone palette each) from managed vertex buffers of 52-byte vertices (FVF 0x115c: position, 3 weights, UBYTE4 palette offsets, normal, colour, uv) through vertex shaders sharing one declaration. Shader 0xf0000006-style: skins with 3 bones (palette at c0.., 3 registers per bone), ramp u = max(0, N.L with light c48), ramp row c48.w; the outline pass (cull CW) pushes the vertex out along the normal by c49.w. Taz is ~2,000 triangles in ~460 batches. Smoothing swaps each batch for a cached PN-triangle copy, 3x3 per triangle; shared edges are computed from a fixed end so neighbouring batches match bit for bit. Before tessellating, each buffer's normals are evened out like `tools/normals.py` (6 nearest positions, 3 rounds, neighbours facing more than 60 degrees away ignored, hard-edge corners kept), at most 6.5 ms once per model. Checked on Taz's original model: same clean shadows as the Blender-evened one. Cache is keyed by (buffer, start, count, type) and dropped when a buffer is created at a cached address. Quickload stress: one heap crash in ntdll in ~150 loads with smoothing on (none in 2 runs since), cause unknown.
- Models (`mesh.c`): `taz-hd\meshes\<FNV-1a of the vertex buffer>.bin` replaces a whole character. Every pass (textured, then outline) draws the same batches in the same order, so the file lists them; each skipped batch hands over its bone matrices (bone i = register r of batch b) and texture, and the last one draws the replacement in groups of up to 16 bones (indexed, 16-bit indices from each group's base vertex; files are read when their buffer first shows up). Replacements skip `smooth_draw`: `tools/subdivide.py` already made them dense, so the runtime PN pass would only add triangles. Taz's buffer is b53721ca228ead11 (same every run). His hands: palm bone, three fingers of two bones each and a two-bone thumb, all rigidly skinned; `tools/hands.py` swaps the six-sided fingers for 10-sided tapered ones with knuckles and blended joint weights (thickness from the old knuckle ring, x1.08, since smoothing puffs the old ones out in game). Checked in game across idle poses (claws, fists) with smoothing on. Cel-shading band edges follow the vertex normals (u = N.L per vertex), so finer tessellation (LEVEL 5) and quadratic PN normals changed nothing visible; `tools/normals.py` averages the model's normals with neighbours (3 rounds, hard edges over ~30 degrees kept except at the ears' inner material, so smoothing rolls their rims round), which made Taz's face, hair and belly shadows clean shapes instead of ragged patches.
- Replacement shaders (`mesh.c`): the game has each character shader kind (lit, outline, a plain one) for 1, 2 and 3 bones per vertex (3, 6 or 9 `dp4 r, v0, c[a0+row]`; seen: f0000002/4/8 3-bone plain/outline/lit, f0000006/7 2-bone, others 1-bone, created as models need them) and picks by the model. A dense replacement of a one-bone character (everyone but Taz) was drawn with the 1-bone shader, which ignores its blended weights, so in-between points snapped to one bone (Gossamer's sawtooth brows, black shards on his body). Replacements now draw with the 3-bone shader of the same kind and constant layout (`shader_for`): levels without fog (12, 19, 20) keep the colour in a different register, and borrowing the fog version drew Taz solid red. Files now carry (magic TZM5, 96 bytes per vertex, stream 1, v6-v13) where each of up to six bones alone puts the vertex, plus the weights and palette registers of bones 4-6; a copy of each 3-bone shader made at creation reads those instead of v0, which equals subdividing the posed original every frame (the dense surface is a fixed blend of the original points; `subdivide.py` gets each bone's share by running the blend on that bone's points alone, sums checked to 0.0001). Older TZM4 files are skipped (that character draws its original model) and need a rebuild. Without this Taz's cheeks and jaw bulged up to 20 px past the original at 2880x1800 whenever the jaw bones moved; three bones per point still left up to 17 units of error at the chin, six leave under 1 (measured on six captured poses). Taz Styles have their own six-bone shader variants. `GetVertexShaderDeclaration` is not implemented in d3d8to9, so the Remaster's shader copies take the declaration from the create call; before that, per-bone Taz drew nothing in Remaster.
- Dense models (`tools/subdivide.py`): two Catmull-Clark levels in Blender take Taz from 2,006 game triangles (3,710 faces after the new hands) to 103,504, and the PN smoothing before them only curved each original triangle on its own, so outlines still kinked at every original vertex. Plain subdivision shrank him (thin arms, blunt hair spikes and teeth; 0.7 units average, 16 at the muzzle), so each original point is put back and the new points get the same correction blended linearly (positions from the same cage subdivided with SIMPLE, which keeps Blender's vertex order). Kept sharp: folds over 60 degrees (creases), open edges (vertex creases, so parts tucked into others don't open gaps), and the eyes plus faces painted with black lines on a lighter texture, with one ring around them (smoothing pushed the brow outline across the pupils and put a dashed line under the eyes). Normals are blended linearly as a corner attribute: Blender's own custom-normal option on the modifier gave speckled cel shading in game, and normals recomputed from the dense surface made the outline pass poke through the eyes. UVs blend linearly (swatch textures). Measured at 2880x1800 in the zoo hub idle, vsync off, 2 runs each: ~108 fps with the old model, ~112 with the dense one (the old one went through the PN cache per group). Files are ~3.5 MB each (0.9 before).
- Character shaders (disassembled, `style.c`): lit pass (vs f0000006-style) c48 light (xyz, world, towards the light; w = ramp row, 0.21875 for Taz and Tweety), c49 camera position, c50 fog (x far, y scale), c51 colour scale; oT1 = (max(v5.z, N.L), c48.w), oD0 = vertex colour (0x7f7f7f7f) x c51; stage 0 MODULATE2X texture x diffuse, stage 1 ramps.png MODULATE (point, clamp u); cull NONE. Outline pass (f0000003-style): c48 colour, c49.w width (1.8), c50 camera, c51 fog; no texture, cull CW. No pixel shader. The device (DXVK) offers ps 1.4, vs 1.1, 8 stages, 256 vertex constants.
- Taz Style (`style.c`, setting taz_style current|cartoon|soft|fur): only player one's model: its vertex buffer is actor (*0x6c8c80) +0x130 -> +0x3c -> +0 (also costumes; the frontend Taz has no actor and keeps the current look). Swaps in our vs 1.1 (same skinning, extra constants c80-c87) and a ps 1.4 per lit/outline draw and restores state after; Taz's textures are told apart by fingerprint (eye frame0 gets a redrawn eye with a catchlight). Measured in the hub idle at 2880x1800: 23.8 fps current, 23.6-24.0 with each style. Reworked 2026-11-15 after a side-by-side (`qa/styles.sh <out>` shoots all four): the edge light now multiplies the fur colour (added cream light turned brown fur salmon pink), the cartoon shadow is warm (a bluish one greyed the cream) and starts at N.L 0, the N.H highlight is masked to dark texels and in the cartoon looks only on the eyes (on the nose's polygons it drew white glints on the cheeks and whitened the whiskers; the nose texture has its own painted shine), and the fur has two maps (front x,y; side z, y + x/2) mixed in a narrow band with tufts about 1.6x wider (a third map for his top swirled into rings, plain z,y gave wood grain, a 50/50 mix wove a cross-hatch).
- Springs (`mesh.c`, file format TZM3): extra bones after the game's, each hanging off a game bone with a pivot and tip in bind space. Once per frame the tip is pulled toward where the parent puts it (stiffness, damping against the parent's own velocity, so steady runs don't drag it), and the spring bone is the parent turned about the pivot by amount x the lag angle, eased toward limit with tanh. `tools/springs.py` gives Taz four (ears, top fur, tail); swings measured in a run: ears ~2 degrees idle, up to ~20 while running and stopping. Damping against world velocity left them pinned at their limits, and Taz's run animation bobs his head hard, hence amount < 1.
- Input (Babel bInput, DirectInput8): logical channels with up to 6 bindings each; FUN_00568630 creates one (value int at +0x14, ±0x7ff8), FUN_00568860 biBindInput(channel, code, code2) binds. Physical codes (FUN_0057be60): 2-4 mouse buttons, 5/6/7 mouse X/Y/wheel (DIMOUSESTATE at 0x751548, mouse device 0x7513a4), 10-41 joystick buttons, 0x2a-0x2f joystick axes, 0x36-0xa0 keys (code -> DIK via the dword table at 0x658770 + code*4). Player pads: 0x6c8090 (P1), 0x6c83b0 (P2), set up by FUN_00489ed0; channel pointers at pad+0x38 x1, +0x3c y1, +0x40 x2, +0x44 y2, +0x60 cross (Jump, C), +0x64 triangle (Bite, R), +0x68 circle (Spin, F), +0x6c square (Rant, D), +0x70 L1 (camera left, E), +0x74 L2 (Tiptoe, X), +0x7c R1 (camera right, T), +0x80 R2 (look around, V), +0x88 start (P), +0x8c select (map, Space); +0xa0.. are the debounced copies. Keyboard defaults: FUN_0048c100 (arrows move; the camera stick has no keys). FUN_00489b90 turns channels into pad floats each frame: [2]/[3] left/right magnitude, [4]/[5] left x/y, [6]/[7] right x/y (-1..1).
- Gamepad (`controls.c`): the game opens joysticks at startup (enum callback 0x57b0e0, called from bInitInput 0x57b020; table at 0x75105c, 0xa4 bytes each: +0 flag 1 = opened, +4 GUID, +0x14 device; axis state 0x75169c, 6 per joystick, 0..65535) but player 1's place is reserved for the GUID saved by config.exe (0x751a98 -> taz.dat copy at 0x6a5d38; all 0xff when none), so with nothing saved every pad was turned away ("No devices available") and pads only worked after config.exe. `init_input` clears that reservation when it is all 0xff; `bind_gamepad` then binds the first joystick for player 1 if its product name says Xbox/XInput (Wine and Windows both: "Controller (XBOX 360 For Windows)"; axes X Y Z Rx Ry = codes 0x2a-0x2e, Z is both triggers, buttons A B X Y LB RB Back Start L3 R3 = codes 10-19). Button channels are analog, so an axis bound to one is on in both directions (why either trigger tiptoes). Menu channels: 0x144/148/14c/150 and 0x154.. up/down/left/right, 0x164/0x174 select, 0x168/0x178 back; menus also take pad cross as select and triangle as back. The game's own camera stick turns the view the opposite way to the mouse and springs the tilt back; `camera_control` flips it and holds the tilt like the mouse (dead zone 0.2). Keys or a pad saved in config.exe make the game skip the keyboard defaults call (so neither our keys nor this); with Controls on WASD `init_input` overwrites player 1's saved id (0x6a5d38) with all ones, so the launcher's setup is ignored; with Classic it is honored (tested 2026-11-19 with a taz.dat holding a zero id at 0x48: the layout was skipped before, bound after; no real config.exe session). The DLL does nothing outside `taz.exe` (`in_game` in proxy.c), since config.exe imports d3d8.dll too. Tested 2026-11-15 under Proton with a uinput virtual pad (`qa/pad.py <fifo>`, start it before the game): sticks, every button, pause and menu navigation. The game never looks for joysticks again after startup, so every 120 frames with none opened `find_gamepad` asks XInput whether pad 0 is there and, if so, runs the game's own enum callback over game controllers and binds; a pad plugged in mid-game worked ~2 s later, and after four unplug/replug cycles (the game's device recovers by itself; `bind_once` skips codes already bound). A quickload to before the pad was plugged in drops it (the joystick table is in the restored globals); quickload now runs `find_gamepad` at once, so the stick worked straight after 4 of 5 loads and after the next one in the fifth (virtual pad, 2026-11-27). Each such load leaves the previous DirectInput device unreleased. Not tested: real pads, Windows.
- Camera control: FUN_004e0f00 (camera at param+4, pad at param+8). L1/R1 swing the camera around Taz at 0x5f7364/fps rad per frame; the right stick swings at that rate times x and tilts via camera+0x64 = camera+0x2e0 + -y * 0x5f73ec (springs back at 0). Camera flags at +0x74 (0x800 look-around mode, 0x8000 stick-only). Look-around (first person) is FUN_004e19a0 / FUN_004e1c00.
- Draw distance (`drawdist.c`, setting `draw_distance` 1/2/4, default 4): three limits, each multiplied. Far plane: FUN_0056aca0(near, far) sets the projection (stored 0x740f14/18, also used for sprite culling); callers pass 0x6c6bfc (near, 50) and 0x6c6c00 (far, default 75000, per scene from its settings x250 in FUN_004a1970; 140000 in the zoo hub and Grand Canyon). Fog: FUN_0056c420(start, end) sets D3DRS_FOGSTART/END and keeps them at 0x741240/44 (+1/(end-start) at 0x741248) for sprites' CPU fog; scenes' FOGMIN/FOGMAX (x250, 0x704d7c/84, flag 0x704d78) only give the ratio, as FUN_0048f430 makes the fog end at the far plane. Object fade: FUN_004ac4e0 calls FUN_00475020(list, start, end, 0, 0, per_radius) on six instance lists (0x702d08 and +0x1514: 10000..12500; the others 3750..5000 plus 2x the object's radius); FUN_00474e70 sets alpha +0x1e6 to 0 past end, fades between (unless scene flag 0x6c6c10), flag 0x100 in +0x1f8 exempts an object. That fade, well inside the fog, is what made things pop in. Depth buffer is already D24S8 (taz.dat zDepth 32), near plane unchanged. Measured in Grand Canyon at 2880x1800, vsync off: ~127 fps original, ~117 at 2x, ~109 at 4x.
- F11 (`settings_frame`) flips HD textures, smoothing, models the Taz style and draw distance off and back on, without saving; F11 is not a remappable key. Shift+H was tried first, but Shift spins Taz in the WASD layout.
- Controls (`controls.c`, setting `controls` wasd|classic, keys per action `key_*` in the ini): wraps the keyboard defaults call (0x48ad3c, 0x48ad74); for player 0 it takes each layout key off every channel FUN_0048c100 binds, then binds it to its action. Live changes (`controls_apply`) clear those channels, rerun FUN_0048c100 and bind the layout again. Channel bindings: slot k at +0x24 + k*0x1c (codes), slot count at +0xcc; wraps the camera control call (0x480e5d) to add mouse X/Y to the pad's stick floats for that call only (right stick normally, left stick in look-around, flag 0x800, whose turn sign is opposite) and turns the camera position (+0x00) by the same angle the game gave its destination (+0x20), since the game eases toward it. Camera points (floats, y up): +0x00 eye, +0x10 look-at (eased after +0x30 at +0x6c), +0x20 eye destination (eye eased after it at +0x68), +0x30 followed actor (+0xa4) + offset +0x40, +0xac actor that places the destination (scripted), +0x60 distance, +0x64 pitch. The stick turns +0x20 around +0x10, which trails a running Taz, so the mod turns eye, look-at and destination around +0x30 instead (a mouse turn came out ~25% short while running). Camera update FUN_004dfef0 (player 1 call at 0x4a8687, cameras at 0x708a50, stride 0x3f0c): eases, then with flag 4 (set with rate +0x70 by FUN_004e0c20 from Taz states in FUN_00482830; never set in the zoo hub) or 0x40 swings +0x20 behind the actor, sets height from the pitch (flag 1) and pulls +0x20 to the distance around +0x30. That pull is a leash: running sideways orbits the camera (~2 rad/s). Once the mouse has turned a camera, the mod restores +0x20's angle around +0x30 after every update (so only the mouse and camera keys turn it), with no time limit unless flag 4 or 0x40 (the game's deliberate swing behind Taz) is set; after the gamepad's stick it holds 1.5 s and fades over 1.5 s. Not with flags 0x800/0x100/0x200 (catch-up path), without 0x1000, or with +0xac set. The eye eases at 0.06 and the look-at at 0.15 per 60 Hz frame, so a sideways run turned the view ~20 degrees toward the motion (measured 2026-11-21, zoo hub); after each update the mod turns the eye around the look-at onto +0x20's heading (at most 4 rad/s). Walls (`pull_in`): while the camera follows Taz, the game's collision ball (+0x278, radius 125) is nulled for the update, since it pushed the eye sideways and shook against the mod's placement. FUN_0045e870(0x7054e8, a, b) is the game's line-against-level test (no camera side effects, answer in AL). The distance +0x60 is shortened for the update to the clear line minus 70; with under 250 clear the camera rises in 23-degree steps up to 69; it moves in at 18/s after 0.1 s blocked and out at 3/s. Measured 2026-11-21 in the zoo hub, including backing Taz into three walls and orbiting there: walls no longer turn the camera, Taz hidden in 0% of mouse samples (31-52% before), worst cost 323 us per frame. Taz's states set the tilt after the camera control ran (FUN_004e0bf0(cam, 0) every frame in spin states 0xc/0xd, FUN_004e0c10 raises the resting tilt +0x2e0 from 0.3 to 0.524 in fall state 0x18), which cancelled vertical mouse look while spinning and tipped the view on every jump; `camera_update` puts the mouse's tilt back (resting tilt 0x649b44 - pitch * 0x5f73ec) before the game's update wherever the game lets the stick tilt. The update eases the eye (+0x00) toward +0x20 before setting +0x20's height from the tilt (y = tan(tilt) * flat distance), so a tilt trailed the mouse by ~30 frames; `camera_update` now lifts the eye around +0x30 by each frame's tilt step after the update (measured 2026-11-19, zoo hub, 15x12 px bursts: view still 2 frames after the last motion, was ~30). Headings wrap at pi: take differences through `wrap` (unwrapped, the fading hand-back threw the camera up to half a turn). Single player uses pad 0x6c83b0; check pad+0x180 (player index), not the address. The DirectInput mouse goes exclusive (hidden, unlimited deltas) only while the camera control ran in the last 2 frames. Tested headless with xdotool mousemove_relative. xdotool motion turns the camera the same with W or W+A held (2026-11-04, zoo hub and safari: 0.675 rad per 15x30 px burst standing, running, running sideways); the dev laptop's only pointer is its touchpad, whose libinput disable-while-typing (on by default) drops motion while any non-modifier key is held and ignores touches begun meanwhile, so "no mouse look while running" there is the touchpad, not the game. Map: 0x4a77f1 opens it (FUN_004c7df0) when the debounced select channel (pad+0xcc, 0x6c847c) is set, FUN_004cbcb0 allows it, and scene 0x704cf0 is not 0, 1, 3, 7, 8, 0xc, 0xd, 0x11, 0x13-0x1d; the zoo hub is scene 3, so no map there. - Ghidra project lives in `re/` (ignored). `make` builds the proxy with mingw-w64.
- Code layout rules: every change to game code goes through `patch.c` (`write_code` with the expected bytes, `write_jump`, `redirect_call`; `patch` for method tables, `patch_import` for imports), never a local VirtualProtect. Game addresses used by more than one file are named in `game.h`. `settings.exe_known` (the retail link timestamp, set once in DllMain) is the one test for "this is the exe those addresses describe"; anything that runs every frame and touches a game address checks it (a gamepad search on another build would have called into nonsense). The mod's own textures are bound with `textures_bind_own` and are not tracked: only textures created from taz.exe's code are fingerprinted (hashing each 1920x1440 video frame took 38 ms, measured 2026-11-18). To check a patching refactor, compare taz.exe's code in memory with the file on disk under the old and new builds: 74 changed runs, same targets (2026-11-18).

FUN_004b8de0 (logged as "saving on the way to scene") is the save writer that runs on scene changes, not the change itself. Scene changes save the game, so back up TazWanted.sav. Costumes are whole separate Taz models with his 46-bone skeleton, so the Taz model scripts work on them. - Mesh capture (`capture.c`): a `taz-hd\capture` file (optionally holding a frame count) records character draws: each vertex buffer once, then per draw its range, stage-0 texture fingerprint and vertex shader constants c0-c95. Constants: c0-c47 bone matrices (3 rows each, bind pose to world; vertex palette offsets are register numbers), c48 light, c49 outline, c92-c95 view-projection. Buffers hold the bind pose (a T-pose for Taz, Y up, ~315 units tall). Taz's buffer has 3,164 vertices (1,039 positions, 2,006 triangles, ~46 bones) and 7 textures; textureless draws are the outline pass. `blender -b -P tools/meshview.py -- <capture> 0 <out.blend>` rebuilds the biggest buffer as a mesh with a vertex group per bone (bones found by matching matrices across batches); `tools/meshshot.py` renders a .blend from four sides, textured and wireframe. Bone poses change every frame at 60 fps (no stepped animation).
- World capture (`capture.c`): a `taz-hd\world` file ("N S": N frames, every S-th) records every 3D draw to the back buffer into `taz-hd\world-NNN.bin`: the draw's vertices (and indices), textures (fingerprints; a scrolling texture's big one, with the proxy's texture transform), world/view/projection matrices, viewport, the render and stage states that decide its look, and c0-c95 for vertex-shader draws (first frame only). Pretransformed 2D (HUD, CPU-projected sprites and sparkles) and other render targets are left out. The first frame is the hero frame and is saved as a screenshot too (the capture drops the `shot` trigger for the next Present); later frames add only draws not seen yet (same vertices, textures and states within 64 units). `blender -b -P tools/worldview.py -- <out.blend> <hero.bin> [sweep.bin...]` rebuilds it (one object per texture for world-space draws, per matrix for placed objects, characters posed on the CPU; materials as the game draws them, Raw view transform). Zoo hub, 2026-11-21: rendered from the captured camera it lines up with the game screenshot within 0.2 px at 13 landmarks (Direct3D's half-pixel centre offset corrected), mean colour difference 1/255 outside the characters. Facts found: the whole hub's static world (~23k triangles, identity world matrix) is drawn every frame whatever the view, only placed props are culled; character shader constants c92-c95 are world x view x projection (so the bone rows give model space); the projection is 12:7 (x 0.873, y 1.497) on a 16:10 screen; world draws are MODULATE2X texture x vertex colour, alpha test > 0 everywhere, no culling; vertex colours are two-tone baked shadows (127 grey lit, 109/100/127 lilac shade) with hard polygon edges. Moving traffic can fill the capture's table, so it stops at 131,072 draws. The first entry to the city plays a long intro flyover, so a capture taken then records the wrong camera.
- Night levels (city hub, scene 8): the colour is blue light baked into vertices over pale textures (lit ground 53/52/127, walls 17/17/43, warm pools 127/127/64 or 127/127/0). `unbake` in `level.ini` keeps their brightness and drops the tint. The lamp table sits on sampler 6; in zoo and city test runs the game never bound a texture above stage 3.
- `tools/pak.py list|unpack|textures` reads `.pc` paks; `textures` writes each unique texture once as PNG plus `index.tsv` (all occurrences). A `.bmp` and `.tga` of the same name with different pixels (9 in all: zoohub_outro zoocloud 1-4, cityhub spotlight_tga, goldmine voodoospell, resTex phoneboxwhite, watersplash, tazwaterdrop) keep their extension (`zoocloud.tga.png`); before, the second overwrote the first's PNG while both fingerprints pointed at it, so the zoo hub outro's cloud ring drew as a dark box and the city's lamp spots as white boxes. Output goes in `extracted/` (ignored). Mostly 64-128 px, max 512; 7,239 unique. `tools/upscale.py` leaves `ramps.png` alone (a cel-shading lookup strip for Taz and She-Devil; upscaling it made their shading blotchy) and only enlarges mostly see-through sprites smoothly (the upscaler hardens glows). One-colour sprites whose antialiased edges step steeply from clear to solid (both font sheets `resTex/yikes` and `voodooyikes`, A4R4G4B4 from the `.ttf` entries, white with 16 alpha levels; music notes, digits, glass cracks) are line art instead: Real-ESRGAN sharpens their alpha, kept within the original's 3x3 alpha range. Bicubic left all game text blurry. Font `.ttf` layout: 1872-byte header with the glyph table at 0x30 (8 bytes each: x, y, w, h as u16; cells 37 px high, 2 px apart), then the 256-wide sheet. It wraps the padding only along axes whose opposite edges continue each other (~3,100 textures don't on some axis: sky panels, grass/path joiners). Many polygons stretch a texture's edge row (the frontend's orange path is the bottom row of `tazfern08`, the zoo hub's sky ceiling the top row of its skybox panels), so wrapping the other edge in turned them olive/navy and drew outlines at panel seams. A colour fit then pulls each upscale's blurred 4x4 averages back to the original (the upscaler drifted colour by ~4 levels on average, up to ~25), and each pixel is clamped to the range of the original's 3x3 neighbourhood: the anime model draws dark outlines and light rims along colour borders (lines across grass and roads, rims on tree tops) that the originals don't have. Median drift after both: ~1.9 levels. Flat-colour details a few pixels wide can come out wrong: the city's grass flowers (`citybloom01`/`02`) as blurry squares, the cowboy costume's one-pixel stubble as squiggles. `FLAT` in upscale.py enlarges those by rounding off each flat colour's area instead (checked in game against F11). Found by scoring each texture with 32 colours or fewer against that rounding (share of pixels off by more than 80 levels; the broken flowers scored 0.059) and looking through everything above 0.03 (405 of 5,216 scored); the rest were fine. Colour swatch sheets and stripes (Sam's `yosamitecolors`, Tweety's, the cowboy hat band `cowboyhatstar`; `blocky` in upscale.py, 73 textures) are enlarged pixel for pixel: the upscaler softened and wobbled their block borders, which models sample by UV.

## Testing and release
- Test rig scripts live in `qa/` (untracked): `stop.sh`, `key.sh` (sends to its copy's gamescope display), `launch.sh` (to the main menu), `tolevel.sh` (into slot One's level), `qsfuzz.sh <rounds>` (random play with F5/F9), `step.sh <out.jpg> [wait] [keys]` (screenshot), `tomenu.sh` (to main menu via `similar.py` + `ref-mainmenu.jpg`), `idletest.sh`, `measure.sh`/`analyze.py` (menu timing), `fresh.sh <prefix>` and `player.sh <prefix> <game dir>` (no-argument start, like a player). `tour.sh <out> <scene>...` jumps to each scene and saves a paused HD/original (F11) screenshot pair, for spotting texture problems level by level. Back up `TazWanted.sav` before runs that might reach a save.
- Fast rig, `qa/fast.sh`: `go [scene]` is the default way into a level: it keeps the running game when the build is unchanged and only changes level (9-14 s including the fade, 1 s if already there; it does not reset a level you are already in), and restarts by itself after a rebuild. `start [scene]` is a clean restart from the save, skipping logos, menus and intros; use it after changing the ini or files read at startup, or to reset state (about 18 s on a quiet machine; 25-126 s measured with 3-5 games running, up to 105 s of it Proton starting), `shaders` recompiles and shows HLSL in the running game (about 4 s), `check quick|full [name]` shoots five fixed views and flags Remaster views that left the approved range (46 s; full takes 2 min and adds all looks, pause, F5/F9, walking, a resize and level changes), `approve <quick|full> <runs>` sets the reference after an intended change. `masks` records what moves in each view; rerun it only if the views change. The test camera moves only the Remaster view, so the HD and Original shots are for reading the sheet. A worktree at `.claude/worktrees/NAME` tests in its own `~/Games/taz-agents/NAME` and prefix `taz-test-NAME`. Hold `flock -x ~/Games/taz-agents/.gpu.lock` around frame-time measurements; rig runs take it shared.
- Test runs: use your own copy, never the dev install, which the user may be playing: `TAZ_GAME=~/Games/taz-agents/<name>` (reflink copy of the dev install, d3d8.dll linked to your build) and `WINEPREFIX=~/.local/share/wineprefixes/taz-test-<name>` (reflink copy of `taz-test`). Proton won't start a game in a prefix that is already running one, so a shared prefix makes agents wait on each other.
- Parallel agents: qa scripts only touch their `TAZ_GAME` copy's game (`qa/game.sh pids|exe|display` finds its processes and gamescope display), and keep their temp files in that folder. Tested 2026-11-04: two headless games side by side, keys reached only their own game, stopping one left the other running. Frame-rate measurements are only valid with no other game running (`pgrep -fc '^[A-Z]:.*taz\.exe'`).
- Release: `tools/package.sh <version>` builds `dist/taz-wanted-hd-<version>.zip` (DLL, `extracted/upscaled` as `taz-hd/textures`, `fingerprints.tsv`, `extracted/videos`, `package/README.txt`, LICENSE). ## Rules
- The game files are verified retail (2026-10-29): `taz.exe` and `TazLauncher.exe` are byte-identical to the disc and known to VirusTotal since 2009 with 0 detections; `binkw32.dll` has 1/71 (Cynet heuristic, first seen 2009). Agents may launch the dev install for testing; recheck hashes if the install is replaced.
- Never commit game binaries, pak files, or anything extracted from them. Public releases ship only our code and our assets.
